# Evidence and provenance

## What is actual execution evidence?

- `authoring/001-v1-baseline`: the uncapped v1 passes before cap tests exist.
- `authoring/002-cap-red-before-implementation`: new cap tests fail against the still-uncapped code.
- `authoring/003-cap-green` and `004-cap-refactor`: passing runs after implementation and after refactoring.
- `authoring/005-coverage-before-boundary`: real V8 coverage and the saved JSON summary.
- `authoring/006-mutation-before-boundary` and `007-mutation-after-boundary`: actual Stryker logs, JSON and HTML reports.
- `agent-runs/`: performed agent or reviewer runs with their exact prompt, unedited output and transcript. `2026-11-03-scene06-fresh-review` is a real fresh-context review of the seeded UI defect.
- `rehearsals/`: independently created workspaces exercised by the rehearsal harness, with raw logs, command exit codes, timing, source fingerprints, actual browser screenshots/traces and blocked/successful packaging evidence.

Each execution JSON records its command, working directory, Node/platform, timestamps, actual and expected exit code, and SHA-256 fingerprints before/after the command. An expected nonzero result is a successful demonstration of the relevant failing check; the child command still exited nonzero. Run locations are absolute historical paths; portable copies of important reports live beside the logs.

These records are generated by local commands, not an external attestation service. Hashes identify source versions; they are not a proof of who authored the code. Execution clocks and durations describe the preparation machine, not a performance guarantee. The application itself has no time-dependent behavior.

## What is prepared teaching material?

All `checkpoints/` source variants and intentionally seeded defects are prepared examples authored during this project. This includes scene 5's agent change (`AGENT-CHANGE.md`), which is not a recorded agent run. The standalone scene-1 build is not claimed to be the raw output of a specific original coding-agent run. The cap's original red execution really preceded its implementation during preparation. Scene replays recreate that sequence but are not themselves proof of the original chronology.

[The prepared review finding](../docs/reviews/prepared-ui-finding.md) is explicitly illustrative. A separate, real fresh-context review is preserved under `agent-runs/`; do not mix the two up, and do not present either as approval of the corrected version.

`prepared-review/` preserves the actual generated input diff, snapshot hashes and prepared prompt. Its diff includes new browser-test contents. Bundle creation was checked, but no independent reviewer output is present or implied.

## Preserving a live agent or reviewer run

Use a fresh, uniquely named directory under `evidence/agent-runs/`. Save the exact prompt actually sent, the full unedited response and available tool transcript, the agent/tool identity, source hashes, commands/results and whether the run completed. Do not edit a response into a success story or relabel a prepared checkpoint as its output. If a run times out, retain that fact and switch to the explicitly labeled fallback.

Prompts in `prompts/` are prepared inputs, not evidence that they were executed. This repository does not fabricate agent transcripts. Ordinary source preparation by the current coding agent is not presented as an independent review.
